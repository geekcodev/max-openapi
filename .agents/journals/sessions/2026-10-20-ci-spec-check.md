# CI-прогон `tools/check_spec.py` (P0 № 1 из `QUALITY.md`)

## Проблема

Проверка спеки запускалась только вручную в сессии. Дрейф от официальной схемы (новый релиз `api-schema`) и появление
незарегистрированного расхождения оставались незамеченными до следующей сессии. Это последний открытый пункт P0 в
`QUALITY.md`.

## Решение

Создан `.github/workflows/spec-check.yml`:

- **триггеры**: `push`, `pull_request`, расписание (понедельник, 06:00 UTC) и `workflow_dispatch`; `concurrency` с
  `cancel-in-progress` по ветке;
- **шаги**: `actions/checkout@v4` → `actions/setup-python@v5` (3.11) → `pip install pyyaml openapi-spec-validator` →
  клон `max-messenger/api-schema` в `official-schema/` → `python3 tools/check_spec.py`;
- путь к официальной схеме передаётся через переменную окружения `OFFICIAL_SCHEMA` (поддерживается `tools/_common.py`);
- сборка красная, когда `check_spec.py` возвращает `1` (новое расхождение **или** устаревшая отметка
  `info.x-official-schema`) либо `2` (сбой валидации / нет официальной схемы).

Сопутствующее:

- `.gitignore` — добавлен `official-schema/` (локальный клон, если кто-то повторит путь из workflow; в CI каталог
  создаётся на раннере);
- `QUALITY.md` — пункт P0 № 1 отмечен выполненным, риск «нет CI» снят, в снимок метрик добавлена строка CI;
- `AGENTS.md` — § 2 (строка состава `.github/`), § 6.2 (правило: красная сборка — повод разобрать расхождение или
  обновить отметку версии), § 7.1 (абзац о workflow и о том, что означают коды возврата);
- `README.md` — строка состава `.github/`, заметка в разделе «Проверка», «Последнее обновление».

Теперь оба пункта P0 `QUALITY.md` закрыты; открыты P1 (`tools/schema_map.yaml`, английский оверлей — отложен) и P2.

## Проверка

- `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/spec-check.yml'))"` — YAML валиден; шаги
  перечисляются в ожидаемом порядке.
- **Симуляция шагов workflow локально** (тот же путь, что в CI): клон схемы положен в `official-schema/schema.yaml`,
  запуск `OFFICIAL_SCHEMA=<...>/official-schema/schema.yaml python3 tools/check_spec.py` → `EXIT=0`, отметка
  `0.0.33 (коммит 1a4a502)`, официальная `0.0.33`, версия совпадает, новых расхождений нет. Попутно подтвердилось, что
  отсутствие git-репозитория по пути клона не ломает проверку — строка с коммитом просто не печатается.
- Ранее в той же сессии проверены режимы отказа: искусственное расхождение и `version: "9.9.9"` → код `1`.
- **Не запускалось:** сам workflow на GitHub (нет прогона на раннере) и линтер workflow (`actionlint` в окружении нет).
  Это честно помечено и в `QUALITY.md` (P0 № 1 — «фактический прогон на GitHub не наблюдался»).
- `python3 tools/check_spec.py` на репозитории — код возврата `0` (103 зарегистрированных отклонения, новых 0).

## Нюансы

- Версии экшенов закреплены мажорными тегами (`@v4`, `@v5`) — простой вариант; пин по SHA строже, но здесь не нужен.
- Расписание специально стоит: между сессиями официальная схема может выпустить релиз, и тогда сборка станет красной без
  правок с нашей стороны — это и есть цель пункта.
- Пункт P0 № 1 закрыт по реализации и локальной проверке; фактическая зелёная сборка появится только после пуша (пуша и
  коммита нет).
